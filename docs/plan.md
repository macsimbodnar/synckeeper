## Workstreams

Statuses: `not started` → `in progress` → `blocked (reason)` → `done (date)`. Work strictly in order within a workstream; W1 blocks everything else (correctness first).

**Execution order on the primary platform (updated 2026-07-18): W1.8 → W1.9 → W4 → W3 → W5.** W3 and W4 keep their identifiers and swap execution order — correctness never depends on the watcher (spec §8.1), so the fuzzer earns more than FSEvents does right now; see decisions.md 2026-07-18 "Roadmap". ### W1 — Correctness fixes (from the 2026-07-17 review) — `done (2026-07-17)` · reopened three times by adversarial analysis (W1.7, W1.8, W1.9 — all closed 2026-07-19)

Reproduced bugs first; each fix lands with its regression test (testing.md R1/R2, plus rows below). **A later adversarial re-analysis found a critical data-loss bug this ordering-focused pass missed — see W1.7 below; that too must be green before W2.**

1. **[R1] Conflict-backup vs move ordering — data loss.** — **done 2026-07-17.** Remote rename to a lexicographically smaller path + remote edit + local edit: `ConflictBackup` sorted before the `MoveLocal` that fed it, backup failed, download overwrote the moved local edit; cycle 2 planned nothing. Fixed per spec §4.5: a true conflict never routes the local content through a move — the backup acts on the file's current location (conflict copy named after it) — and actions carry `ProtectedBy`, refused by the executor when their backup failed. Tests: see testing.md R1 (engine + reconcile + executor levels).
2. **[R2] MkdirLocal-before-MoveLocal — permanent livelock.** — **done 2026-07-17.** Remote same-id dir rename + new remote subdir inside it: the mkdir stage `MkdirAll`ed the move destination; `MoveLocal` then failed `file exists` every cycle. Fixed with the ordering fix per spec §4.5: plan stage order is now dir-moves → mkdirs → file-moves/backups → transfers → deletes. Dir moves depend on nothing the plan creates; file moves stay after mkdirs because a `MoveRemote` may target a folder a `MkdirRemote` creates. Tests: see testing.md R2.
3. **`init --force` leaves a stale remote mirror** — **done 2026-07-17.** It reset the page token without rebuilding the cache → silently missed remote changes. Fixed per spec §12: `initialize` now calls `remotedelta.ForceFullWalk` (fresh token + mirror rebuild in one step); a fresh `init` gets a pre-warmed mirror as a side benefit. Test: testing.md R3.
4. **Download overwrite window** — **done 2026-07-17.** Downloads now carry the local state the plan assumed at the target (scanned size/mtime, or "absent" for conflict-vacated and edit-beats-delete targets); the executor re-stats immediately before the atomic rename and refuses on any drift — the racing local write wins the cycle and the next cycle resolves it as an ordinary conflict. Tests: testing.md R4.
5. **Read-only commands can migrate the DB without the lock** — **done 2026-07-17.** `statedb.OpenRead` accepts only an exact schema-version match (older → "run `sync` once with this binary"; newer → "binary too old"; missing DB never created); `openReadEnv` uses it, treating a missing DB as not-initialized. Migrations now run only under the instance lock (spec §14). Test: testing.md R5.
6. **Swap-rename sweep** — **done 2026-07-17, and the review's "self-heals" analysis was wrong.** The verification test exposed *silent permanent divergence*: after the swap's moves half-failed (FS renamed, DB rolled back), an unprotected `Record` stamped the planned md5 onto whichever file sat at the path — a poisoned baseline the scanner trusted forever. Fixed by extending `ProtectedBy` to local moves (records/uploads of a moved file are refused when its move failed) and by `Record` verifying the scanned stat before overwriting the baseline (invariant 7). The transient unique-constraint move failures remain as accepted noise; convergence to the *correct* state within ~4 cycles is now pinned by the test. Tests: testing.md R6.

### W1.7 — Adversarial-analysis correctness fixes — `done (2026-07-17)`

Reopened W1 after an adversarial re-analysis found a confirmed critical data-loss bug the ordering-focused W1 review missed. Same discipline (red-first regression tests, suite + `-race` green). Blocks W2. See decisions.md 2026-07-17 "W1.7 (R7/R8/G3)".

1. **[R7] `MoveLocal` clobbers an untracked local file at the move destination — silent data loss.** — **done 2026-07-17.** A remote rename/move onto a name that already exists locally `os.Rename`d over the local file (no conflict copy, no quarantine, reported as success). Fixed with the R4 pattern generalized to moves: reconcile preserves an untracked occupant as a conflict copy (backed up before the move, uploaded, move `ProtectedBy` the backup) and stat-pins a tracked occupant (safe to clobber, e.g. the R6 swap); the executor re-stats the destination and refuses an unexpected occupant. Tests: testing.md R7 (reconcile + engine + executor).
2. **[R8] `ConflictBackup` overwrites an existing destination.** — **done 2026-07-17.** Same unguarded-rename class; the executor now refuses a rename onto an existing conflict-copy path (crash leftover), replanning with a fresh timestamp. Tests: testing.md R8.
3. **[G3] Mass-delete guard aborted the whole cycle (spec §6/§8.1 deviation).** — **done 2026-07-17, C1.** The daemon now defers only the delete-class actions and keeps syncing everything else, surfacing the block in `status`; the interactive one-shot still aborts with the `--confirm-deletes` hint. New `engine.Options.DeferMassDelete` + `Result.GuardBlocked/GuardReason`. Tests: testing.md G3.

### W1.8 — Adversarial-analysis correctness fixes, round 2 — `done (2026-07-19)`

Reopens W1 again after a second adversarial analysis (2026-07-18, run against the goal/plan/spec once W2 closed) found nine defects, each reproduced with a throwaway test before being reported. Same discipline as W1.7: **red-first regression test, then the fix, then the testing.md row, suite + `-race` green at every commit.** Blocks everything else. See decisions.md 2026-07-18 "W1.8".

Work strictly in this order — item 1 is the choke point everything after it is written against, and items 2–3 are the highest user-visible impact.

1. **[GATE] The local-write gate — one choke point, mechanically enforced.** — **done (2026-07-18).** New `internal/executor/localwrite.go` becomes the only file in the package permitted to mutate a local path: `guardedRename` / `guardedRemove` / `guardedStat` over a single `expectation{exists, size, mtimeNS}`. Port all five primitives onto it — `download` (`executor.go:507`), `moveLocal` (`:323`), `conflictBackup` (`:380`), `record` (`:559`), and **`quarantineLocal` (`:581`), which had no guard at all (A7)**. Expectations map straight across: backup = zero value (absent), quarantine/record = pinned scanned stat, download/move = what the plan assumed, so `Action.LocalExists/LocalSize/LocalMtimeNS` is already the wire format and no new plan surface is needed. Closing A7 also means reconcile stat-pins `QuarantineLocal`, exactly as R4 stat-pinned downloads. Companion test walks the package AST and fails on any `os.Rename`/`os.Remove`/`os.RemoveAll`/`os.Create`/`os.OpenFile`/`os.WriteFile`/`os.Truncate`/`os.Chtimes`/`os.Link`/`os.Symlink` outside the gate file *(ban list extended 2026-07-18, plan review — `os.WriteFile` was the obvious one-call bypass)*. One recorded exemption outside the package: `doctor --repair`'s prefix-matched orphan-temp removal (`doctor.go:233`) stays outside the gate — spec §7 names it. Amends spec §7. Tests: R13 + the gate's structural test. *Implementation notes (2026-07-18):* the expectation stays the three-field wire format as decided; absence-when-expected is a per-primitive policy, preserving the two decided behaviors (moves proceed — R7's sibling-vacated case; downloads/records/quarantines refuse — R4's one-rule) rather than inventing a unified one. `moveFile` moved into the gate (its copy fallback uses banned calls), temp cleanup routes through `removeOwnTemp` (refuses non-`.synckeeper.tmp.*` names), and the empty-dir remove keeps `os.Remove`'s non-empty refusal as its guard. The gate test was verified to catch a planted violation.
2. **[A1] Local directory renames are moves, not delete + recreate.** — **done (2026-07-18), together with C1/R18.** `reconcile.Plan` pass 2 `continue`s on `loc.IsDir` before the move-pairing block (`plan.go:256-265`), so directories are excluded from local-driven pairing; pass 4 then trashes the orphaned baseline dir (`plan.go:374-377`). Reproduced with no concurrency: renaming `Docs/` → `Papers/` plans `mkdir_remote` + per-file `move_remote` + `trash_remote`, and the Drive folder id changes.

   **Approach is decided — implement it, don't re-derive it** (decisions.md 2026-07-18 "W1.8.2"). *Share the representation, not the detection.* Keep two detectors feeding one `dirMove` list and one `rewrite()`:
   - *Remote-driven* stays as-is (`plan.go:52-82`): same file id at a different remote path.
   - *Local-driven* is **collapsed out of the file pairing that already happens.** The file pass already computes `Docs/one.txt → Papers/one.txt` for every child and discards the pattern — that is the entire bug. Pair baseline dir D → new location N when: D is absent locally; **D's remote is unchanged** (same precondition file pairing already uses); at least one tracked descendant paired as a move; and **every** surviving paired descendant landed under N preserving its subpath relative to D. Deleted descendants don't block (their own `TrashRemote` covers them); a descendant paired *elsewhere* does block — that's a scatter, not a rename. No surviving children → no evidence → delete + create, unchanged and intended.
   - Emit **one** `MoveRemote{IsDir:true}` and **drop** the per-file moves it explains: a Drive reparent carries the whole subtree.
   - *Why conservative:* a missed pairing costs a churned folder id (today's behaviour, and harmless once item 3 lands); a wrong pairing reparents an entire remote subtree including remote-only files the plan never reasoned about.

   **Two traps, both verified against current code:**
   - **The moves-stage split must stop keying on `IsDir`.** `plan.go:398-405` hoists every `IsDir` move ahead of the mkdirs (that hoist is R2's fix — a `MkdirLocal` scaffolding a rename destination is a permanent livelock). But a local-driven dir move is a `MoveRemote`, touches no local path, and must run *after* the mkdirs like every other `MoveRemote`, since its destination parent may be a folder `MkdirRemote` has yet to create (`plan.go:396-397` already says so for files). Predicate becomes `Type == MoveLocal && IsDir`. Within the post-mkdir stage, dir `MoveRemote`s order **before** file `MoveRemote`s, top-down — a file moving into the renamed folder resolves its parent via `pathIDs`, which only learns the new path when `renamePathIDs` runs (`executor.go:357`).
   - **`moveRemote`'s commit drops `IsDir` and would corrupt the baseline.** `executor.go:358-373` calls `RenameItemPath` (which already renames descendant rows — `statedb/items.go:85-116`) and then `UpsertItem` with no `IsDir`; `UpsertItem` deletes-then-inserts (`items.go:61-75`), so the folder row returns as `is_dir = 0` and pass 1 then treats it as a file. Set `IsDir`, or skip the upsert and let `RenameItemPath` stand alone — and don't `os.Stat` for size/mtime/md5, which mean nothing for a directory. **Round 3 (2026-07-18) proved the *file* case of this same commit is live data corruption (C1, test R18):** the upsert records the destination's *current* stat with the *scanned* md5, so an edit landing between scan and commit poisons the baseline — local and Drive diverge silently and permanently, reported as success (reproduced; the R6 class at a sixth commit site). The fix is trap 2's, made general for both files and dirs: **the commit never restates local truth** — `RenameItemPath` keeps the row's scanned stat + md5, only the Drive-side fields (`drive_md5`, `drive_version`) are refreshed, and there is no `os.Stat` at all. Red test R18 lands with this item.

   **The §4.4 interaction is decided (2026-07-18, plan review): remote-side rows resolve under N.** Remote children of D the pairing didn't explain — added or edited concurrently on another machine — are planned at their post-reparent location under N (the reparent carries them there): remote-only creations download into N, edit-beats-delete downloads land in N, and the plan never scaffolds a zombie D/ after deciding D moved. Mechanically this is the shared `rewrite()` applied to **the side that hasn't moved yet**: remote-driven dir moves rewrite local/baseline paths (as today), local-driven dir moves rewrite remote paths — sharing the list without honoring that direction plans downloads into the dead D/. R9 gains both concurrent-change cases. Amends spec §4.3. Test: R9. *Implementation notes (2026-07-18):* the "drop the per-file moves" fell out structurally — once a dir collapses, pass 1 judges its children at their post-rename paths (§4.2's post-move rule applied to the side the user moved), so the per-file moves are never emitted rather than emitted-and-removed. Detection gained two conservative guards in the decided rule's spirit: N must be a brand-new local dir (a tracked destination is a merge, not a rename) and N's name must be free on the remote side (a reparent onto an occupied name would mint a duplicate — the C2 class). The reparent slots into the stage order after the mkdirs and before the file moves, with remote mkdirs that target a just-reparented dir deferred behind it (spec §4.5 note). C1/R18 landed in the same change: `moveRemote`'s commit is `RenameItemPath` + a Drive-fields-only update — no stat, no restated local truth, `is_dir` preserved (both traps closed by the same shape).
3. **[A2] The mass-delete guard counts content, not containers.** — **done (2026-07-18).** Falls out of A1 but fix it independently as belt-and-braces: `guards.CheckMassDelete` counts only file-class deletions against tracked non-directory items. Reproduced: renaming one folder with 20 subfolders = 21 delete-class actions / 41 tracked items → the one-shot aborts demanding `--confirm-deletes`, and the daemon defers the deletes without changing the state that produced them, so it replans the same 21 every cycle and stays **permanently guard-blocked**. Verify both halves: one-shot no longer aborts, daemon no longer wedges. Amends spec §6, adds acceptance G4. Test: R10.
4. **[A4] Decision-table rows resolve at post-move paths.** — **done (2026-07-18).** Pass 2 looks up `newRemoteAt(p)` at the *pre-move* path (`plan.go:266`) while emitting the action at `target`, the post-move path (`plan.go:255`, `:295`) — the directory branch three lines above already uses `target` (`plan.go:261`), which is what makes this an oversight rather than a decision. Consequences: spec §4.2's `absent | new | new, diff md5` → conflict never fires (no conflict copy for the local content), and the plan emits `upload B/x` **and** `download B/x` into the same parallel stage. Amends spec §4.2. Test: R11.
5. **[A5] Enforce spec §4.5's concurrency rule instead of assuming it.** — **done (2026-07-19).** `reconcile.ValidateTransferStage`, called by `executor.Apply` before anything journals; the reconcile test harness validates every planned scenario as a property net. One precise exemption: a **directory Record** commits a DB row only and cannot race a child's file I/O, so it is exempt from the ancestor/descendant rule (not the same-path one) — a blanket check would refuse the real dir-adopt + child-download plan. No code anywhere implements "same rel_path, or an ancestor/descendant pair, never run concurrently"; `executor.Apply` fans the transfer stage into 4 workers with no overlap check (`executor.go:139-159`). Add a pre-execution assertion so a planner mistake is a refused plan, not a race — this catches A4's class mechanically. **Scope (corrected 2026-07-18, plan review): the assertion covers the transfer stage only** — the only concurrently executed stage. Serial stages sequence overlapping paths *by design* (nested mkdirs, bottom-up deletes, R7's backup-then-move on one rel_path); a blanket same-stage check refuses those correct plans and goes red on S8. Amends spec §4.5. Test: R12.
6. **[A3] `reload` must publish hot config safely.** — **done (2026-07-19).** The loop publishes an atomic ignore-glob snapshot (`publishIgnore`) that the pump and `watchSubtree` load; `applyReload` republishes on swap. One narrowing verified at implementation (decisions.md "W1.8.6"): `w.Poll` has **no off-loop reader** — every read is on the sync loop — so it stays a plain loop-owned write; the race was the ignore globs alone. Red-first: R14 generates a file-write storm during 25 reloads and the pre-fix code races exactly as predicted. Confirmed under `-race`: `applyReload` writes `w.Eng.Cfg.Engine.Ignore` (`control.go:123`) while the fsnotify event pump reads it per event (`watch.go:234`, and via `watchSubtree` at `:279`); `w.Poll` (`control.go:127`) is the same shape. The method's comment ("runs on the sync loop, so no cycle is concurrently reading the config") is true for cycles and false for the watcher goroutine. The suite is race-clean today only because no test reloads while events flow — so the regression test must generate event load. Amends spec §8.3. Test: R14.
7. **[A6] The daemon never exits on a watcher-rebuild failure.** — **done (2026-07-19).** The rebuild branch now degrades exactly like the `pollingOnly` branch (nil watcher, polling-only, cadence retries); **scope extended one site** (decisions.md "W1.8.7"): the startup `startNotifier` call had the identical `return err` shape, so a daemon that cannot create a watcher at launch now starts polling-only per §10's universal fallback instead of refusing to run. Red-first via two test seams (`newNotifyWatcher` injection + a test-only rebuild cadence); R15 pins degrade → still-syncs → watching restored, plus the startup case. Original finding: `watch.go:171-177` returned the error from `startNotifier`, killing the daemon — against `Run`'s own doc comment, spec §8.1 ("without exiting") and §10 ("falls back to pure polling"). The `pollingOnly` retry branch ten lines above (`:162-167`) handles the identical error by degrading, which is the tell. Trigger is `fsnotify.NewWatcher()` failing under fd pressure — precisely what the surrounding latch machinery exists for. Code fix only; spec is already correct. Test: R15.
8. **[A9 + A8] Two low-severity hardening items.** — **done (2026-07-19).** (a)'s red test corrected the analysis (decisions.md "W1.8.8"): the crash shape did **not** converge benignly — the plan was `MoveLocal` (refused by the §7 gate every cycle, destination occupied) **plus** the `TrashRemote`, so "convergence" happened only by destroying the moved folder. Two-part fix: pass 4 skips the trash when a local **dir** sits at the id's current remote path (a dir absent from both local paths stays a real deletion — trash still propagates, pinned by a companion case), and the executor completes a dir `MoveLocal` whose disk half already happened as a commit-only replay (§4.6's self-healing made real; no local mutation, so the write gate is untouched). (b) `Snapshot` gained a visited set mirroring `prune`'s; red test pins termination on the one root-reachable cycle the single-parent schema allows. Original findings: (a) a crashed directory `MoveLocal` — renamed on disk, DB not yet committed — plans `TrashRemote` for the dir when it is empty (`plan.go:374-377`: `hasCreateUnder` and `remoteAliveUnder` both false); a crash produced a remote delete, the shape invariant 6 exists to rule out. (b) `remotedelta.Snapshot`'s BFS has no visited set (`remotedelta.go:240-285`) — unlike `prune`'s directly above (`:168-179`) — so a parent cycle in the cache is an infinite loop in the daemon. Tests: R16, R17.

### W1.9 — Adversarial round-3 fixes (code analysis, 2026-07-18) — `done (2026-07-19)`

A third adversarial code pass, run after the round-2 plan was frozen. Five defects reproduced with throwaway probes (probes deleted, tree left clean, suite green), two more found by inspection. The worst — C1, the `moveRemote` commit poisoning the baseline — **folds into W1.8.2**, which already rewrites that exact commit (see the amendment there; red test R18). The rest is this workstream: **after W1.8, before W4**. Same discipline: red-first regression test, then the fix, then the testing.md row, suite + `-race` green at every commit. See decisions.md 2026-07-18 "W1.9".

1. **[C2] Cross-tree fold collisions get the conflict they were owed.** — **done for files (2026-07-19); the directory arm is a recorded follow-up** (decisions.md "W1.9.1": a new local folder fold-equal to a remote folder still mints a duplicate folder — closing it needs the case-only-rename arm of the §7 gate for dirs, the same family as W1.8.8's R7-dir-arm note; MANUAL.md entry narrowed accordingly, not retired). Implementation: fold-keyed sibling index consulted by pass 2 after the exact match misses; the adopt lands via a **case-only `MoveLocal` to the remote byte form** with the §7 expectation pinned to the file's own scanned stat (the destination "occupant" is the source itself under the fold); shadowed ids (fold **and** duplicate-name skips, both carry `FileID` now) held harmless in passes 1 and 4 via `Input.ShadowedRemote`. Reproduced on APFS: local `Readme.txt` + remote `README.txt`, both new, different content → cycle 1 blind-uploads a **case-duplicate onto Drive** (permanent; on real Drive "first by id" makes the winner nondeterministic across machines), cycle 2 fold-collapses the siblings, our own upload loses, the baseline row reads "remote-deleted" → the user's file is **quarantined**; the §4.2 both-new conflict never fires. Spec §5's "names are compared under fold wherever the local FS folds them" was implemented only for remote siblings. Decided approach (targeted — a full fold-keyed re-key of reconcile was rejected as a wide refactor of the most load-bearing code): (a) new-local vs new-remote matching consults a **fold-keyed sibling index** when the FS folds, so fold-equal names fire the ordinary §4.2 adopt/conflict, remote winning the canonical byte-form; (b) a baseline row whose file id was **fold-skipped from the snapshot is held harmless** — surfaced as a skip, never treated as remote-deleted (no quarantine, no trash). Amends spec §5. Test R19.
2. **[C3] Directory quarantine sweeps invisible leftovers.** — **done (2026-07-19).** `sweepInvisibleLeftovers` (in the gate file, per the §7 exclusivity rule) moves ignored-or-temp entries into the dated quarantine destination before `guardedRemoveEmptyDir`; temp files sweep even when no ignore pattern covers them, and a cross-volume rename fails the action and replans (accepted — the leftover may be a subtree; decisions.md "W1.9.2"). Executor gained the `Ignore` list from engine config. Reproduced: remote deletes `docs/` while the local copy holds a `.DS_Store` (default-ignored; Finder drops one into every browsed folder) → `quarantine_local docs: directory not empty` **every cycle, forever** — A2's wedge shape with a different trigger. Fix: before removing the dir, move remaining entries that are **ignored-or-temp** into the quarantine destination (preserving subpath); anything else still refuses, unchanged — an unexpected survivor means the plan is wrong. Amends spec §3 (invariant 3 note). Test R20.
3. **[C4] Quarantine never overwrites a rescue copy.** — **done (2026-07-19).** `uniqueRescueDest` numbers the suffix before the extension (`f (2).txt`); beneath it `guardedMoveFile` refuses any occupied destination, so a race between the name pick and the rename replans instead of clobbering. Reproduced: two same-day quarantines of one rel_path — the second `os.Rename`s over the first, silently destroying the earlier rescue copy (Drive trash still held it, which caps the severity). Fix: the quarantine destination **uniquifies on collision** (numbered suffix), and `moveFile` refuses an existing destination instead of clobbering. Amends spec §3 (invariant 3 note). Test R21.
4. **[C5] Type clashes are skips in every direction.** — **done (2026-07-19).** Pass 2 skips-and-claims both directions (new local file vs remote folder, new local dir vs remote file); pass 3 checks the local occupant's type before MkdirLocal/Download. One convergence note (decisions.md "W1.9.4"): a *tracked* file remote-replaced by a folder still quarantines first and materializes the folder the next cycle — one cycle slower than before, never an error loop. Reproduced: remote folder `x` + untracked local file `x` → `mkdir_local x` fails every cycle **and** pass 2 blind-uploads the file, minting a same-name file-beside-folder pair on Drive; the mirror direction (remote file vs local dir) error-loops on the refused download. Pass 1 already has the rule — "type clash; report and leave both sides alone" — passes 2 and 3 get the same: on a type mismatch at one rel_path, emit a skip, no transfer, no delete, no upload beside it. Amends spec §4.2. Test R22.
5. **[C6] PKCE on the OAuth loopback flow.** — **done (2026-07-19).** `oauth2.GenerateVerifier` + `S256ChallengeOption` on the URL, `VerifierOption` on the exchange; two test seams (swappable endpoint + browser-opener) let R23 drive the whole loopback flow against a fake token endpoint and prove S256(verifier) equals the promised challenge. Original finding: the client secret is public by design (spec §9), so an intercepted authorization code is exchangeable by anyone; the loopback listener and crypto-random state are right but incomplete. Amends spec §9. Test R23.

Resolved without a work item: **C7** — spec §5 promised ignore-pattern matches are "always reported" while both the scanner and `Snapshot` silently drop them; resolved **spec-side** the same day (ignored matches are silent by design — the user chose the patterns; everything else stays always-reported). ### W2 — Spec alignment & hygiene — `done (2026-07-18)`

1. Remove `full_rescan_interval_secs` (config, validation, reload, docs) — spec §13. — **done 2026-07-17.** Field dropped from `EngineConfig`, its default, validation, and the `reload` hot-copy; the reload test TOML no longer sets it. ### W4 — Confidence: randomized sync testing (spec §16.7) — `not started` · **runs before W3** (2026-07-18)

1. **[FZ1]** Seeded fuzzer over the fake backend: N simulated machines, random op streams (create/edit/move/delete/case-rename/conflict), random crash points at executor checkpoints, interleaved syncs. Invariants: eventual convergence, no content loss (every written content survives somewhere legitimate), idempotence of replays. Deterministic replay from seed on failure.
2. **Oracle additions decided 2026-07-18 — not optional.** (a) **Identity stability, scoped to renames the pairing evidence supports** *(scoping corrected 2026-07-18, plan review)*: a rename of an **unmodified** file, or of a directory with surviving paired children, preserves the id and plans zero delete-class actions. Unscoped, the oracle flags decided-correct behavior as failure — the empty-dir rename (delete + create by design, R9) and §4.3's unpaired edit-and-rename remainders; the fuzzer generates the ops, so it knows which renames qualify. (b) **§4.5 structural invariant:** no two actions in the **concurrent transfer stage** on one rel_path or an ancestor/descendant pair (shares W1.8.5's assertion, same scoping — serial stages sequence overlapping paths by design). Rationale: W1.8's A1 converges and loses no content, so the originally specced oracle would have passed it clean.
3. **Op menu must include** the classes that have actually shipped bugs, not just the tidy ones: remote move onto an existing local name (W1.7's R7), same-cycle cross-rename swaps (R6), a new local file under a remotely-moved directory (W1.8's A4), directory renames on both sides (W1.8's A1), fold-colliding names created across machines (W1.9's C2), type clashes at one rel_path (W1.9's C5), and delete/recreate churn against the quarantine (W1.9's C4).

## Working process

1. A workstream item is done when its code, tests, and doc updates land together; check items off here with a date **and rewrite [status.md](status.md)** (last/current/next) before ending the session.
2. Every scope change, spec deviation, or non-obvious choice gets a dated entry in [decisions.md](decisions.md) before or alongside the change.
3. [testing.md](testing.md) rows are the acceptance ledger — add the row with the feature, not after.
4. README build/run instructions stay correct at every commit.
5. The spec is kept current: behavior changes edit spec.md in the same change, marked with a dated note.
6. **`MANUAL.md` (project root) is the end-user manual and ships true at every commit** *(rule added 2026-07-18)*: any user-visible change — commands, flags, config, defaults, behavior — and any known-bug status change (found or fixed) updates it in the same commit. A fix that closes a Known-bugs entry removes that entry in the fix's own commit.
